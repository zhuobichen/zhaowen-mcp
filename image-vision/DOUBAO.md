# 豆包后端（本地豆包桌面版生图）

`image-vision` 的 `generate_image` 有两条后端：

| 后端 | 怎么选 | 实测 |
|---|---|---|
| `http`（默认） | 不设 `IMAGE_PROVIDER`，或传 `provider:"http"` | 走 one-hub。`gpt-image-2-ca` 约 0.4–0.5 分钟/张；`gpt-image-2.5` **2–4 分钟/张**，且**中转不回报模型名** |
| `doubao` | 设 `IMAGE_PROVIDER=doubao`，或单次传 `provider:"doubao"` | 本地豆包桌面版，**从零生图约 15–35 秒/张、2048×2048 PNG**；**图生图（edit_image）也能走，实测约 37 秒** |

豆包这条是**用 CDP 驱动豆包桌面版自己的对话界面**实现的（往它的 tiptap 输入框打字 → 回车 → 等图 → 取原始字节）。没有调任何官方 API，用的是你已经登录的那个客户端。默认**接着当前那个会话发**（见下方 `DOUBAO_NEW_CHAT`）。

`generate_image` 和 `edit_image` **都支持这个后端**（图生图是把底图当参考图塞进对话，见下）。

## 怎么开起来

```cmd
:: 1) 用一个独立 profile 启动带调试端口的豆包（脚本见同目录）
start-doubao-debug.cmd

:: 2) 在那个新窗口里扫码登录一次（登录态存在 profile 里，之后不用再扫）
:: 3) 让 image-vision 默认走豆包
::    在 .claude.json 里给 image-vision 的 env 加：
::      "IMAGE_PROVIDER": "doubao"
::    （改完要重启会话才生效）
```

> **profile 的位置与体积**：脚本用的是 `D:\github_project\ZhaoWen_GitHub维护\_doubao-profile`
> （**仓库外**）。实测它有 **1.9 GB / 5042 个文件**，一度被我放进 `image-vision/` 里，
> 那样会被误提交、也会撑爆仓库，所以挪出来了。**登录态存在这个 profile 里** ——
> 换路径就要重新扫码，别随手搬。

冒烟测试（不经 MCP，直接调模块）：

```cmd
set IMAGE_PROVIDER=doubao
npx tsx test-doubao-smoke.ts "画一只戴帽子的小猫，白底"
```

## 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `IMAGE_PROVIDER` | `http` | `doubao` 时 `generate_image` 走豆包 |
| `DOUBAO_CDP_URL` | `http://127.0.0.1:9333` | 调试端口；端口改了要同步 |
| `DOUBAO_MIN_PX` | `512` | 判定「成图」的最小边长 |
| `DOUBAO_TIMEOUT_MS` | `240000` | 等图超时 |
| `DOUBAO_NEW_CHAT` | `false` | 是否每次点「新对话」。**默认接着当前会话发** —— 只是要一张图，不值当每次开新会话（开一次要等页面切过去，豆包那边也会攒一堆只发过一句话的会话）。设成 `true` 才每次开新的 |

> **复用会话不是省一步那么简单，它给判据加了要求**：当前会话里已经有上一轮的
> `receive_message` 和成品图，所以发送前**必须**拍一张"页面上已有哪些图"的快照并排掉，
> 不然 `waitForImage` 会在发送后第一次轮询就把**上一轮的旧图**当新结果返回
> （跟"把自己送进去的底图当成结果"是同一类错）。两条路径都已接上。
> 另外每次开始前会查一次输入框里有没有**上一轮失败残留的附件** —— 有就刷新页面清掉，
> 免得新老两张图一起发出去（改图场景）或把"从零生图"悄悄变成"改图"。

## 三个必须知道的坑

**1）产物有两个水印，本模块不做裁剪。**
- **可见水印**「豆包 AI 生成」烙在右下角**像素里**（不是叠加层）
- **AIGC 元数据**写在 PNG 的 XMP：`{"Label":"1","ContentProducer":"doubao","ProduceID":"..."}`
  （国标 TC260 那套）。这条反而是**有用的证据**：one-hub 那条通道**不回报模型名**，
  而豆包的产物**自带出处**——所以 `.meta.json` 里把 `aigcMarker` 单独存了一份。
- 裁不裁是用图的决定，擅自裁会让人以为图是"干净"的，所以留给你。

**2）判「成图」必须按像素尺寸，不能按字节大小。**
实测页面里一堆 48×48 / 128×128 的气泡和图标，只按大小筛会把「正在输入」的加载图
（紫色圆 + 白气泡）当成成图存下来 —— 第一次就是这么错的。所以判据是
**`naturalWidth/naturalHeight ≥ DOUBAO_MIN_PX`**。若提示词合规但迟迟不出图，
先把 `DOUBAO_MIN_PX` 调低看是不是判据问题。

**3）读 AIGC 标记时，XMP 里的 JSON 是 HTML 实体转义的。**
文件里写的是 `ContentProducer&quot;:&quot;doubao&quot;`（不是真引号）。不先解实体，
`"key":"value"` 的提取正则一个都匹配不到，函数返回 null —— **看着像"这张图没有标记"，
其实是解析器没读懂**。而且锚点必须落在 JSON 的**左花括号**上：锚在 `ContentProducer`
上会把第一对键值切掉一半，读出来的对象里**恰好没有 `ContentProducer`**。
（两个坑都是实测撞出来的，见 `doubao.ts` 里的注释。）

## 图生图（`edit_image`，2026-10-14 实测可用）

把底图当**参考图**塞进豆包的对话，再打字让它改。用法与 `http` 那条完全一致：

```jsonc
// edit_image 的入参
{ "prompt": "把这张图的背景换成纯白色，把标题文字改成深红色，其他内容保持不变",
  "images": ["D:/some/底图.jpg"],
  "provider": "doubao" }        // 或把 IMAGE_PROVIDER 设成 doubao
```

实测（900×383 的宣传图 → **2272×960**，约 **37 秒**）：产出里**版式、图形位置、所有小字**
（`127.0.0.1 only` / `~/wechat/db_storage` / `github.com/...`）**原样保留**，只改了被点名的两处；
底图长宽比 2.35 → 产物 2.367。所以它很适合「改配色 / 改一行字 / 换背景」这类**保版式**的活。

也试过**换风格的重构**：把 2048×2048 的扁平插画吉祥物（戴蓝渔夫帽的猫）发进去，
要它「保留造型特征与配色、改成有体积感的 3D 卡通渲染」，**28 秒**出来一版
帽子的布料质感、毛发、腮红、坐姿和胡须都保住了。多图（2 张拼一张）实测也通，**28 秒**。

> `size` 参数在这条路上**无效** —— 豆包客户端里选不了输出尺寸。
> meta 里 `requestedSize`（请求的）和 `size`（**实际**产出的）是分开记的，别混。

### 这段代码里踩过的坑（都写在 doubao.ts 的注释里，改之前先看）

1. **附件要用 `DOM.setFileInputFiles`，别用合成 paste 事件。**
   页面内 dispatch 一个 `ClipboardEvent('paste')`（带 DataTransfer）会被豆包处理**两遍** → 挂上
   **两张一样的图**；而且跟 `bubbles` 无关（`bubbles:false` 也是两张），所以不是冒泡到祖先监听器。
   `setFileInputFiles` 是精确 **+1**。
2. **「附件就绪了没有」要看上传链路，别看 DOM。**
   缩略图的 `naturalWidth` 不可信：实测同样两步操作，一次缩略图 900×383 正常、一次 `naturalWidth=0`
   （输入框里是个灰方块），但那次上传链路（`prepare_upload` → TOS → `CommitImageUpload`）是完整的。
   拿 nw 当判据就会把"已经挂上了"误判成"没挂上"。
3. **发送前光标必须折叠，不能全选。** tiptap 里 Enter 的含义取决于选区：
   光标折叠 = **提交**；有选区（全选）= **用换行替换选区**，消息根本不发。
   （从零生图那条路没事，是因为它 `insertText` 之后光标本来就是折叠的 ——
    在它后面多加一次全选反而会把它弄坏。）
4. **别用「输入框变空」或「页面文字变长」判断发出去了没有 —— 两个都会假阳性。**
   全选 + Enter 会把文字替换成一个换行，`innerText` 同样是 `"\n"`；
   而失败那次实测页面文字也长了 64 个字符。可靠的判据只有：
   **提示词出现在页面里、但已经不在输入框里**。
5. **附件清不掉。** 附件不是文档节点，`execCommand('selectAll'/'delete')` 对它无效
   （实测 4→6→8 只增不减，而输入框 `innerText` 一直是空的）。要清场只能**刷新页面**。
6. **「哪张图才是它画的」必须按应用的语义找，不能按尺寸猜。** 这条代价最大：
   最早的成图判据是「页面上自然尺寸 ≥ `DOUBAO_MIN_PX` 的图，取最后一张」，
   结果送一张 **2048×2048** 的底图让它重构时，**13 秒就"成功"了，产物与输入 MD5 一字不差**
   —— 它抓的是**我自己送进去的那张底图**。之前几次没撞上纯属侥幸：
   900×383 的底图**高度**低于阈值、多图那次两张挤在一起被渲染成小缩略图。
   根子上就不成立：**底图多大是我控制的**。
   现在按豆包自己的标记找：用户消息是 `[data-testid="send_message"]`、
   助手回复是 `[data-testid="receive_message"]`，**只在后者里面找图**。
   页面上一个 `receive_message` 都没有时**直接报错**，不退回去按尺寸猜 ——
   判断依据瞎了的时候，静默返回一张错图远比报错危险。
   冒烟测试里因此加了一条**逐字节比对**：产物 MD5 绝不许等于任何输入图
   （尺寸、文件大小、肉眼都靠不住，只有哈希是确定的）。

## 不支持什么

- **指定具体型号**：豆包客户端里是会话，选不了型号，所以 `requestedModel` 记的是
  `doubao (桌面版)`、`reportedModel` 为 null。**不拿请求值冒充回报值**是这个模块一贯的规矩。
- **指定输出尺寸**：`size` 传了也没用（见上），实际尺寸看产出。

## 安全边界

**开了调试端口 = 本机任何进程都能驱动这个豆包实例**（等于给它开了个本地后门）。
所以 `start-doubao-debug.cmd` 用的是**独立 `user-data-dir`**：这个实例只用来生图，
丢了也不影响日常对话。**不建议给日常那个豆包加端口。**
